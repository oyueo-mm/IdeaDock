# 로딩 성능

Word 문서에서 아이디어를 많이 가져온 뒤 목록과 상세가 느리다는 보고를 계기로 병목을 측정하고 고쳤습니다. 이 문서는 측정 방법, 원인, 변경 내용, 전후 수치와 측정의 한계를 기록합니다.

## 측정 방법

`npm run bench`가 모의 Drive 정적 빌드에서 `tests/perf/drive-load.perf.ts`를 실행합니다. 결과 JSON은 `bench-results/`(git 제외)에 저장됩니다.

- 데이터: 아이디어 200개 × 리비전 3개(리비전 파일 600개) + 폴더 8개 + 공유 이미지 25개. Word 가져오기 뒤의 Drive 모습에 가깝게 시드했습니다(`tests/support/seed-drive.ts`).
- 네트워크: 모의 Drive가 Drive의 실제 페이지 크기(1000)로 응답하고 **요청마다 80ms**를 더합니다. 실제 Drive의 지연이 아니라 요청 수에 비례하는 비용을 비교하기 위한 값입니다.
- 계측: Drive 요청 수(목록/다운로드/업로드), IndexedDB `get`/`put` 호출 수, 메인 스레드 long task, 화면 반응 시간.
- 반복: 전후 각각 3회, 같은 컴퓨터·같은 세션에서 측정하고 **중앙값**을 비교합니다. 이전(`94f8b5a`)은 별도 worktree에서 같은 벤치마크로 측정했습니다.

실제 Drive, 실제 계정, 실제 모바일 기기의 수치가 아닙니다. 절대값보다 요청·읽기·쓰기 횟수의 감소가 의미 있는 결과입니다.

## 원인

| 병목                                                                               | 증상                                                            |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 리비전 파일을 **한 개씩 순차로** 다운로드                                          | 600개 × 80ms ≈ 48초                                             |
| 로그인 직후 두 경로(계정 초기화, 연결 완료)가 **같은 파일을 동시에 각각** 내려받음 | 다운로드가 필요한 수의 2배 이상                                 |
| 동기화마다 **모든 리비전을 IndexedDB에서 읽고, 해시를 다시 계산하고, 다시 씀**     | 변경이 없어도 15초마다 읽기·쓰기 각 약 600회                    |
| 업로드 전 중복 확인과 이미지 조회가 **전체 목록**을 조회                           | 파일이 늘수록 느려짐                                            |
| 같은 이미지를 쓰는 여러 썸네일이 각각 내려받고 검증                                | 중복 다운로드                                                   |
| 완료 체크가 `updated_at`을 갱신해 목록이 재정렬됨                                  | 항목이 움직이고 보던 스크롤 위치를 잃어 다른 썸네일을 새로 받음 |
| 첫 화면과 같은 시점에 검증 작업이 시작됨                                           | 캐시된 목록 표시가 그 작업과 경쟁                               |

메인 스레드는 막히지 않았습니다(long task 0ms, 느린 Drive에서도 상세 열기 약 100ms). 병목은 네트워크 요청 수와 중복 처리였습니다.

## 변경

모든 변경에서 **체크섬 검증, 충돌 보존, 오프라인 초안 보존은 그대로**이며, 리비전 저장 방식과 데이터 모델은 바꾸지 않았고 과거 리비전을 지우지 않습니다.

- `src/lib/revision-loader.ts`: 리비전은 파일 키가 곧 SHA-256인 불변 문서입니다. 한 번 검증한 리비전(원격 바이트 또는 기기 캐시 사본)은 이번 세션의 메모리에 보관하고, **처음 보는 파일만** 6개씩 병렬로 받아 각각 해시를 확인합니다. 변경이 없으면 IndexedDB를 읽거나 쓰지 않습니다. `revisions(true)`(강제)는 모든 파일을 원격에서 다시 검증합니다. 변조된 기기 캐시는 원격에서 다시 받아 교체합니다.
- 동시에 들어온 조회는 하나로 합치되, **업로드가 끝난 뒤에는 그 전에 시작된 조회를 재사용하지 않습니다**(오래된 head를 부모로 삼아 가짜 충돌이 나는 것을 막기 위함).
- `DriveRepository.list()`/`FolderRepository.list()`는 리비전 집합이 같으면 같은 행 배열을 돌려주고, 화면은 이를 보고 재구성·재렌더·IndexedDB 스냅샷 쓰기를 건너뜁니다. 그래프 구성은 O(n²)에서 O(n)으로 바꿨습니다.
- 업로드 전 중복 확인과 이미지 조회는 해시로 좁힌 Drive 질의를 씁니다. 루트 폴더 조회는 30초 동안 재사용합니다. 읽기 요청은 429/503에서 두 번까지 재시도합니다.
- 동시 동기화는 하나로 합칩니다(`use-ideas.ts`의 `sync`). 숨겨진 탭은 폴링하지 않고 보이게 되면 따라잡습니다. 첫 동기화는 캐시된 목록이 그려진 **뒤**에 시작합니다.
- 이미지: 같은 해시의 동시 요청을 하나로 합치고, 동시 다운로드를 4개로 제한하며, 실패는 기억하지 않고 썸네일이 자동으로 재시도합니다(1.5초, 3초, 6초). 캐시 사본도 매번 체크섬을 확인합니다.
- 목록: 정렬·필터 결과를 메모이즈하고, 화면 밖 행은 `content-visibility: auto`로 렌더를 건너뜁니다.
- 완료 체크: 보고 있던 순서를 유지합니다(아래 참고).

- 첫 행 표시와 캐시 재실행 첫 행(282ms → 241ms)은 편차가 커서 큰 차이라고 말할 수 없습니다. 이 구간은 원래 빨랐고(캐시 한 번 읽기 + 렌더), 주된 개선은 로그인 직후 동기화, 반복 동기화, 요청 수입니다.
- 첫 로그인의 10.6초는 모의 지연 80ms × (리비전 608개 ÷ 동시 6개)에 가깝습니다. 실제 Drive에서는 요청 한 건당 지연과 속도 제한(429)에 좌우됩니다.
- 체크박스의 Drive 저장 시간은 변하지 않았습니다. 저장은 업로드 2회 + 읽기 검증 1회로 이루어지고, 안전을 위해 건너뛰지 않았습니다. 화면은 저장을 기다리지 않습니다.

## 완료 체크 시 위치 고정

원인: 완료 상태를 바꾸면 `updated_at`이 현재 시각이 되어 "최근 수정순"에서 항목이 맨 위로 이동했습니다. 연속 체크 중 다른 항목을 누르게 되는 사고가 났습니다.

- 체크하기 직전의 목록 순서를 보관하고, **보기가 바뀔 때까지**(정렬·필터·태그·폴더 변경, 또는 고정 상태 변경) 같은 순서를 씁니다. 정렬을 직접 바꾸거나 다른 화면에 갔다 오면 최신 정렬이 적용됩니다.
- 선택 상태, 오른쪽 상세 패널, 스크롤 위치는 그대로입니다.
- **미완료/완료 필터**: 조건에 맞지 않게 된 항목은 사라지지 않고 제자리에서 흐리게 표시되며 "완료로 이동됨"/"미완료로 이동됨"이라고 알립니다. 같은 자리를 다시 눌러 되돌릴 수 있고, 아래로 밀리는 항목이 없어 다음 클릭이 의도한 항목에 닿습니다. 헤더의 **목록 정리(N)** 를 누르거나 다른 화면으로 이동하면 필터가 적용됩니다.
- Drive에 저장되는 값(`is_completed`, `updated_at`, 버전)은 이전과 같습니다.

## 다시 측정하려면

```powershell
$env:BENCH_LABEL="run"; npm.cmd run bench        # 결과: bench-results/run.json
$env:SHOT_LABEL="after"; npm.cmd run bench -- explorer-shots   # docs/screenshots/explorer-ux/
```

`BENCH_IDEAS`(기본 200)와 `BENCH_LATENCY`(기본 80)로 규모와 지연을 바꿀 수 있습니다.

## 남은 한계

- 캐시 스냅샷은 여전히 아이디어 전체를 한 값으로 IndexedDB에 씁니다. 수정할 때마다 전체를 복제·저장하므로 수천 개 규모에서는 증분 저장이 필요할 수 있습니다. 데이터 형식을 바꾸지 않기 위해 이번에는 손대지 않았습니다.
- 목록은 가상화(windowing)하지 않고 `content-visibility`로 화면 밖 행의 렌더만 건너뜁니다. 1,000개 이상에서는 가상 스크롤이 더 낫습니다.
- 실제 Google Drive와 실제 기기에서의 체감 속도는 측정하지 못했습니다.
