# Google Drive 전환 및 안전한 이전

작업 기준: `429b6c3`, 브랜치 `feat/drive-safe-migration`. 기존 main, Supabase SQL·Storage 정책·클라이언트는 변경하거나 삭제하지 않았습니다. 원본 저장소 삭제 API는 이전 절차에 없습니다.

## 연결 설정

1. Google Cloud의 IdeaDock 프로젝트에서 Google Drive API를 활성화합니다.
2. OAuth 동의 화면에서 앱과 테스트 사용자를 설정합니다. 웹 애플리케이션 OAuth 클라이언트를 생성하고 실제 접속 origin을 승인된 JavaScript 원본에 등록합니다. 로컬에서는 `http://localhost:3000`과 `http://127.0.0.1:3000`을 사용하는 주소에 맞게 등록합니다.
3. `.env.example`을 `.env.local`로 복사하고 공개 클라이언트 ID를 `NEXT_PUBLIC_GOOGLE_CLIENT_ID`에 설정합니다. 클라이언트 secret은 브라우저 코드에 넣지 않습니다. `NEXT_PUBLIC_STORAGE_BACKEND`는 비워 두면 Drive 모드입니다.
4. 기존 Supabase가 있다면 기존 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`를 유지합니다. 기존 데이터를 읽는 데 필요하며 신규 Drive 저장에는 사용하지 않습니다. 기존 계정은 작업 공간 설정의 **이전 Supabase 계정 연결 · 데이터 조사용**으로 연결합니다.
5. 개발 서버를 다시 시작하고 **Google로 시작하기**를 누릅니다. OAuth 동의는 연결 승인이고, 데이터 이전 승인은 별도 버튼입니다.

기본 Drive 권한은 `drive.file`, 사용자 확인은 `openid email profile`입니다. 첫 저장 시 일반 Google Drive에 **IdeaDock** 폴더를 만들고 앱 식별자로 찾아 재사용합니다. 같은 이름의 다른 폴더를 임의로 사용하지 않습니다. 문서 이력·이미지·승인한 복구 백업은 이 폴더 안에 저장합니다. `drive.file`은 앱이 만들거나 접근 허가받은 파일에 적용됩니다. [Google Drive 권한 문서](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [폴더 생성 문서](https://developers.google.com/workspace/drive/api/guides/folder)

이전 구현의 숨김 저장 영역이 필요하면 `NEXT_PUBLIC_GOOGLE_DRIVE_SPACE=appDataFolder`를 명시하고 Google Cloud에 `drive.appdata`도 설정합니다. 이 옵션에서는 기존과 같은 `appDataFolder` 및 기존 계정 캐시를 사용합니다. 기본 폴더 모드와 업로드 체크포인트·계정 캐시는 분리하며, 숨김 데이터를 자동 이동하거나 삭제하지 않습니다. [Google 앱 데이터 영역 문서](https://developers.google.com/workspace/drive/api/guides/appdata)

실제 연결 준비 시 필요한 로컬 설정은 다음과 같습니다. Client ID만 로컬 편집기로 입력하고 Client Secret이나 액세스 토큰은 파일·채팅·로그에 넣지 않습니다. `.env.local`은 Git에서 제외됩니다. 기존 파일이 있으면 복사로 덮어쓰지 말고 필요한 키만 수정합니다.

```dotenv
NEXT_PUBLIC_GOOGLE_CLIENT_ID=여기에_OAuth_Client_ID
NEXT_PUBLIC_STORAGE_BACKEND=drive
```

승인된 origin이 `http://localhost:3000`이면 이 주소로 접속합니다. `127.0.0.1`과 다른 origin이므로 임의로 바꾸지 않습니다. 설정을 저장한 뒤 로컬 서버를 재시작하고 **Google로 시작하기**에서 테스트 사용자로 직접 계정 선택·동의합니다.

토큰은 메모리에만 보관합니다. 새로고침과 토큰 만료 후에는 다시 로그인해야 합니다. IndexedDB 초안은 남으며, 설정의 **Google Drive 다시 연결**로 재시도합니다. 미저장 초안이 있으면 계정 변경과 로그아웃을 막습니다. 동일 앱·동일 Google 계정으로 다른 기기에서 로그인하면 서버 데이터가 조회됩니다. [Google 토큰 모델](https://developers.google.com/identity/oauth2/web/guides/use-token-model)

## 데이터 존재 여부 확인

앱의 **기존 데이터 이전 · 백업 · 가져오기 → 저장소 다시 조사**에서 확인합니다.

| 대상                   | 조사 방법                                                                                                 | 확인하지 못하는 경우                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 체험 및 기존 기기 초안 | 현재 origin의 `ideadock:data:*`를 읽고 ideas와 pending을 검증                                             | 다른 주소·브라우저·프로필 데이터는 접근 불가                      |
| 기존 IndexedDB         | IdeaDock 이름의 기존 DB를 열고 저장소를 읽기 전용으로 확인. 아이디어 레코드 배열 또는 단일 캐시 형식 인식 | 목록 API 미지원, 접근 오류, 모르는 스키마는 확인/검토 필요로 표시 |
| 새 IndexedDB           | `ideadock-drive-v1/kv`에 초안·체크포인트·백업. 로그인 시 계정 캐시를 복구                                 | 이미 Drive 계정 데이터이므로 레거시 이전 대상으로 재등록하지 않음 |
| JSON 백업              | 사용자가 파일을 선택하면 검증하고 수정 가능한 미리보기 제공                                               | 파일을 선택하지 않으면 확인 필요. 데이터 없음으로 판단하지 않음   |
| Supabase               | 기존 설정과 인증 세션이 있으면 `list_ideas` RPC 전체 결과 확인                                            | 설정·로그인·연결 실패는 확인 필요. 빈 저장소로 취급하지 않음      |

**이번 개발 세션에서 사용자의 기존 브라우저 프로필과 운영 Supabase에 직접 접근하지 않았습니다. 실제 데이터의 유무는 아직 미확인입니다.** 현재 프로젝트 폴더에는 기존 환경변수·JSON 백업·`만들거.docx`가 제공되지 않았습니다. Git clone은 브라우저 데이터를 복원하지 않습니다. 기존 데이터를 사용하던 정확한 주소와 브라우저에서 조사하거나 그 환경에서 JSON 백업을 내려받아 가져오세요.

브라우저가 알지 못하는 IndexedDB 구조나 손상된 캐시가 나오면 원본을 보존하고 중단합니다. 빈 저장소에는 이전 작업을 만들지 않습니다. 기존 IndexedDB를 새로 만들거나 업그레이드하지 않습니다.

## 사용자 절차

1. 저장소를 조사하고 이전할 원본을 선택합니다. 휴지통도 포함되며 개수와 이미지 수를 표시합니다. 동일 ID의 서로 다른 내용은 자동으로 합치지 않습니다. JSON은 미리보기에서 제목·본문·상태·항목 구성을 수정한 뒤 결과 확인을 누릅니다. 미리보기의 원본 JSON도 백업에 보존합니다.
2. **무결성 검사 및 복구 백업 만들기**를 누릅니다. 문서 구조, ID·관계, 날짜, 상태, 태그·링크·이미지 참조를 검사하고 모든 이미지 원본을 읽습니다. 하나라도 누락되거나 읽기 실패하면 중단합니다.
3. 아이디어 원본, 캐시의 미저장 초안, 이미지 바이트, SHA-256을 포함하는 백업을 IndexedDB에 기록하고 다시 읽어 확인합니다. **이미지 포함 복구 백업 다운로드**로 별도 파일도 보관합니다.
4. Google 연결 후 대상 계정과 이전할 아이디어 수를 확인합니다. 체험 데이터가 있으면 **체험 모드 데이터를 Google Drive로 이전**, **이전하지 않고 기존 Google Drive 데이터 사용**, **나중에 이전**을 선택할 수 있습니다. 뒤의 두 선택은 원본을 변경하지 않습니다.
5. 다운로드한 복구 백업을 보관했다는 체크 후 **Google Drive로 데이터 이전 승인**을 누릅니다. 현재 변경 내용이 미저장이면 먼저 저장해야 합니다. 승인한 계정·백업이 일치하지 않으면 실행하지 않습니다.
6. Drive에 복구 백업 → 이미지 → 문서 순서로 업로드합니다. 실패하면 원본과 백업은 그대로 남으며 **이전 재시도 승인**으로 다시 실행할 수 있습니다. 새로고침 후에는 같은 Google 계정에 연결하고 보관된 백업을 선택하거나 다운로드한 복구 백업 파일을 불러옵니다.
7. 서버 문서와 이미지 바이트를 다시 읽고 일치 여부를 검증한 뒤 완료를 표시합니다. 실제 다른 기기에서도 Google 연결 후 완료·고정·태그·링크·본문 서식·이미지·휴지통·복원을 직접 확인하세요.

## 보존과 멱등성

- Idea의 ID, 제목·plain_text·Tiptap JSON 전체 구조, 완료·고정·태그, 링크 ID와 내용, 이미지 ID·파일명, 생성·수정·삭제일, version 및 알 수 없는 추가 필드를 보존합니다. 계정의 `user_id`와 이미지 저장 경로만 목적지에 맞게 매핑하며 본문 `ideaImage` 참조도 함께 변경합니다.
- `provenance`는 원본 저장소·원본 ID·원본 소유자·원본 내용 체크섬을 기록합니다. 새 아이디어에는 이 정보가 없고 이전한 아이디어에는 목록에 표시가 붙습니다. 원래 경로와 소유자를 포함한 정확한 원본은 복구 백업에 있습니다.
- 이미지는 바이트 SHA-256 기반 `drive-sha:` 참조를 사용합니다. 같은 바이트를 다시 이전해도 논리적으로 같은 이미지입니다. 서로 다른 기기에서 같은 파일을 동시에 생성했을 때 생길 수 있는 물리적 파일 중복도 해시 기준으로 하나의 논리 레코드로 읽습니다.
- 파일 ID를 먼저 발급받아 IndexedDB에 기록한 뒤 업로드합니다. 네트워크 응답을 잃어도 같은 ID로 재시도하고, 409 응답 뒤에는 실제 내용을 내려받아 체크섬을 검증합니다. 재시도 단위는 파일·아이디어입니다. 진행 중이던 파일 자체는 처음부터 다시 전송할 수 있습니다. [Google 사전 발급 ID 및 업로드 문서](https://developers.google.com/workspace/drive/api/guides/manage-uploads)
- 문서는 덮어쓰지 않는 변경 이력으로 저장합니다. 같은 이전을 여러 번 실행해도 동일 이력 해시를 재사용합니다. 이전 후 편집한 최신 이력은 그대로 유지합니다. 같은 원본 ID의 내용이 바뀌었거나 이미 다른 데이터로 존재하면 덮어쓰지 않고 검토를 요청합니다.
- 두 기기가 같은 부모 버전에서 수정해도 양쪽 이력을 남기고 충돌을 표시합니다. 충돌 해결 시 다른 기기 초안을 복사본으로 보존하며, 명시적으로 **내 변경 버리기**를 선택한 로컬 초안만 버립니다. 자동 병합은 하지 않습니다.
- 검증은 이전 스냅샷의 전체 문서 비교와 이미지 SHA-256 재조회입니다. 이후 사용자가 편집한 최신 내용이 이전 스냅샷과 다른 것은 정상이며, 기존 이력에서 이전본의 존재와 일치를 검사합니다. 실제 기기 간 조회 확인은 자동 완료로 간주하지 않습니다.

## 실패와 롤백

이전 실패 시 일부 파일이 Drive에 남을 수 있습니다. 원본과 기존 Drive 데이터를 삭제하는 자동 롤백은 하지 않습니다. 백업과 체크포인트를 보관하고 동일 백업을 재시도하세요. 손상·첨부 누락·권한 오류·할당량 초과·ID 충돌은 검증 완료로 표시하지 않습니다.

기존 버전은 main의 `429b6c3`에 남아 있습니다. 작업 버전에서도 `.env.local`의 `NEXT_PUBLIC_STORAGE_BACKEND=legacy`를 설정하고 서버를 재시작하면 보존한 Supabase 클라이언트로 돌아갑니다. 이 설정은 Next.js 빌드 시 적용되므로 배포에서는 재빌드가 필요합니다. 기존 localStorage와 Supabase DB·이미지를 그대로 사용할 수 있습니다. Drive에서 새로 편집한 내용은 Supabase로 자동 역동기화되지 않습니다.

복구 파일만으로 체험 모드를 복원할 수도 있습니다. 다른 IdeaDock 탭을 닫고 체험 모드에서 나온 상태에서 복구 JSON을 선택하고 검증한 뒤 **복구 백업을 체험 모드에 병합 승인**을 누릅니다. 첨부를 data URL로 바꾸어 기존 버전도 읽을 수 있는 캐시 형식으로 저장합니다. 기존 아이디어는 보존하고 같은 ID의 다른 내용이 있으면 중단합니다. 변경 전 체험 캐시도 별도 복구 키에 보관합니다. 저장 공간이 부족하면 오류를 표시하며 현재 체험 데이터를 지우지 않습니다.

실제 검증 전까지 Supabase 테이블·Storage, 기존 계정 캐시·체험 데이터·복구 파일을 삭제하거나 앱 데이터 제거 기능을 사용하지 마세요.

기기 저장 공간 부족으로 IndexedDB에 기록하지 못할 때도 설정의 **현재 데이터 JSON 백업**은 이미지 포함 복구 파일을 직접 다운로드할 수 있습니다. 이전 업로드는 복구 백업의 기기 기록과 재조회가 성공할 때까지 차단합니다.

## Import 확장

`migration.ts`의 `ImportAdapter` 및 `importAdapters`는 파일 식별과 `preview()`로 분리되어 있습니다. 현재는 JSON만 구현했습니다. Word는 추후 어댑터에서 원본 문서·이미지를 보존하며 제목만 있는 항목, 긴 설명, 구분선을 후보 단위로 나누고, Tiptap 문서로 변환한 결과를 편집 가능한 미리보기로 반환합니다. 업로드는 어댑터가 직접 하지 않고 공통 백업·승인·검증 절차를 사용해야 합니다. `만들거.docx`는 아직 제공되지 않아 분석·가져오기를 수행하지 않았습니다.

## 검증 범위와 제한

2026-10-27에는 별도 브라우저 프로필에서 실제 Google 로그인과 `drive.file` API 연결을 검증했습니다. IdeaDock 폴더 1개, 테스트 아이디어 생성·수정 이력의 SHA-256, 새로고침 후 같은 계정 재로그인과 제목·본문·완료·태그 재조회를 확인했습니다. 체험 데이터의 실제 이전은 실행하지 않았습니다. 구체적인 결과와 제한은 [실제 검증 기록](VALIDATION.md)을 확인하세요.

자동 테스트는 모의 데이터와 모의 OAuth/Drive API를 사용하며 실제 사용자 데이터를 이전하지 않습니다. `npm run test:e2e:drive`는 전용 포트 3001과 가짜 공개 클라이언트 ID로 실행됩니다. 실제 Google 인증 동의, 운영 API 권한·할당량·CORS, 기존 Supabase 및 물리적 두 기기 검증은 설정 후 별도로 수행해야 합니다.

현재 동기화는 15초마다 서버 변경 이력을 조회하는 단순 구현입니다. 이력이 많은 계정의 성능 최적화, 토큰 재인증 전 완전한 오프라인 기동, 대용량 파일의 바이트 단위 전송 재개, Word 어댑터는 후속 범위입니다. 원본과 이력의 자동 삭제·가비지 수집은 제공하지 않습니다.
