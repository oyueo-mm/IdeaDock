# 가져오기 성능

JSON(아이디어 27개, 이미지 1장, 약 250KB)과 Word 가져오기가 느리다는 보고를 계기로, 선택부터 최종 검증까지 단계별로 측정하고 병목을 고쳤습니다. 측정 방법, 원인, 변경과 안전 장치, 전후 수치, 측정의 한계를 기록합니다.

## 측정 방법

가져오기 대화상자는 이제 **단계별 소요 시간과 Drive 요청 수·평균 응답 시간**을 완료 후 보여 줍니다(`단계별 소요 시간` 목록). `GoogleDrive`가 요청 수와 응답 시간을 세고(`stats()`), `StageTimer`가 단계마다 차이를 기록합니다.

벤치마크는 실제 대화상자를 Playwright로 조작합니다(`npm run bench -- json-import`, 결과는 `bench-results/`).

1. JSON 파일 선택 → **미리보기** 표시
2. **수정한 결과 확인** → 항목 목록
3. **복구 백업 만들기**(기기에 저장하고 다시 읽어 검증)
4. **Drive 저장**: 복구 백업 업로드 → 폴더 → 이미지 → 아이디어 → 최종 서버 재조회 검증
5. 완료 표시

- 데이터: 아이디어 27개와 이미지 1장이 든 JSON(244KB). 저장소가 비어 있는 경우와 **기존 아이디어 200개가 있는 경우**.
- 네트워크: 모의 Drive가 요청마다 **80ms 또는 300ms**를 더합니다. 모의 Drive는 Drive의 페이지 크기(1000)로 응답하고, 실제 Drive의 속도 제한은 별도 시험으로 흉내 냅니다.
- 요청 수는 모의 Drive가 종류별로 셉니다(목록, 다운로드, ID 발급, 업로드 시작, 업로드 본문). 평균 응답 지연은 앱이 직접 잰 값입니다.

실제 Google Drive와 실기기에서는 측정하지 못했습니다. 절대 시간보다 **요청 수와 직렬 구간의 감소**가 의미 있는 결과입니다.

## 원인 (개선 전)

아이디어 하나를 저장하는 데 **요청 5개가 순차로** 나갔습니다.

| 요청                          | 왜                                | 필요한가                               |
| ----------------------------- | --------------------------------- | -------------------------------------- |
| 목록 조회(해시로 좁힘)        | 같은 내용이 이미 있는지 확인      | 배치로 한 번이면 충분                  |
| ID 발급 `generateIds?count=1` | 파일 ID를 미리 받아 기기에 저장   | **한 번에 N개** 받을 수 있음           |
| 업로드 세션 시작 (POST)       | Drive의 재개 가능 업로드 프로토콜 | 필요(아래 참고)                        |
| 내용 업로드 (PUT)             | 본문 전송                         | 필요                                   |
| 읽어서 체크섬 비교            | 올린 바이트가 맞는지 확인         | 검증은 필요하지만 **최종 단계와 중복** |

그 밖의 병목:

- 이 모든 것이 **아이디어마다 순차**였습니다(요청 지연 × 요청 수 × 아이디어 수).
- **최종 검증이 모든 리비전을 다시 내려받았습니다.** 기존 아이디어가 200개이면 가져온 27개와 무관한 232개 파일을 다시 받았습니다.
- Word 가져오기는 **항목마다** 전체 리비전을 강제로 다시 내려받고(O(저장된 수 × 항목 수)), 이미지도 항목마다 전체 이미지 목록을 조회했습니다.
- 복구 백업 두 개를 각각 따로 업로드했습니다.

로컬 단계(미리보기, 백업 생성)는 1초 미만이어서 병목이 아니었습니다.

## 변경

**유지한 것** 불변 리비전, 내용 해시 이름, 체크섬 검증, 복구 백업(기기·Drive), 계정 격리, 업로드 전 ID 저장, 실패 후 재실행 안전성.

- **일괄 쓰기** `DriveRepository.putMany/appendMany/saveMany`: 종류별 목록을 **한 번** 조회하고, ID를 **한 번에** 발급하고(기기에 저장한 뒤에야 업로드), 최대 **3개씩 병렬**로 올립니다.
- **재시도 정책** `upload-pool.ts`:
  - 일시적 오류(429, 403 속도 제한, 5xx, 연결 끊김)만 재시도합니다. 시도는 최대 4번, 대기는 `500ms × 2ⁿ + 무작위 지터`입니다.
  - 속도 제한 응답을 받으면 허용 동시성을 **절반으로 줄이고**(최소 1), 연속 8번 성공하면 하나씩 되돌립니다.
  - **재시도도 동시성 슬롯을 거치므로** 재시도가 몰려 속도 제한을 키우지 않습니다.
  - 영구 오류(400대 등)는 재시도하지 않고, 이미 진행 중인 업로드는 끝까지 마칩니다.
- **응답 유실 안전**: 재시도 전에 **해시로 목록을 조회**해, 응답만 잃은 업로드를 중복 생성하지 않습니다. 실패한 실행을 다시 눌러도 같은 ID와 해시를 씁니다.
- **검증은 한 번, 최종 단계에서**: 일괄 쓰기는 업로드 직후 읽기를 생략하고(`readBack: false`), 최종 **서버 재조회 검증**이 이번 실행이 쓴 리비전·폴더·이미지만 다시 내려받아 해시와 내용을 비교합니다. 기존 아이디어 파일은 다시 받지 않습니다. 이미 Drive에 있던 파일은 항상 읽어서 비교합니다.
- Word 가져오기도 같은 경로를 씁니다(백업 두 개를 한 번에, 이미지 한 번에, 아이디어 일괄 저장, 최종 검증 한 번). `revisions(true)` 전체 재다운로드는 사라졌습니다.
- 복구 백업 업로드도 재시도를 거칩니다.

업로드 세션(POST)과 본문(PUT)을 한 요청으로 합치는 **multipart 업로드**는 요청을 파일당 1개 더 줄이지만, 실제 Drive에서 확인할 수 없어 적용하지 않았습니다. 실제 계정으로 검증할 수 있을 때 가장 효과가 큰 다음 단계입니다.

## 전후

아이디어 27개 + 이미지 1장(JSON 244KB). 시간은 Drive 저장 단계(승인 클릭부터 검증 완료까지)이고, 개선 후는 3회 중앙값(편차 1% 이내)입니다. 개선 전은 시나리오마다 1회 측정했습니다(요청 지연이 지배적이라 편차가 작습니다).

| 시나리오   |  지연 | 개선 전 |    개선 후 |  배 | 요청 수 전 → 후 |
| ---------- | ----: | ------: | ---------: | --: | --------------: |
| 빈 저장소  |  80ms |  15.8초 |  **4.7초** | 3.4 |   181 → **101** |
| 빈 저장소  | 300ms |  50.7초 | **13.6초** | 3.7 |   190 → **101** |
| 기존 200개 |  80ms |  22.8초 |  **5.8초** | 3.9 |    382 → **99** |
| 기존 200개 | 300ms |  62.9초 | **13.9초** | 4.5 |    392 → **98** |

300ms, 기존 200개 시나리오의 단계별(시간 / 요청 수):

| 단계                     |        개선 전 |        개선 후 |
| ------------------------ | -------------: | -------------: |
| 복구 백업을 Drive에 저장 |      2.2초 / 6 |      2.2초 / 6 |
| 이미지 저장              |      1.6초 / 5 |      1.3초 / 4 |
| **아이디어 저장**        | **44초 / 149** | **7.0초 / 57** |
| **서버 재조회 검증**     | **14초 / 232** | **2.6초 / 30** |

요청 종류(300ms, 기존 200개): 목록 45 → 8, 다운로드 260 → 29, ID 발급 29 → 3, 업로드 시작·본문 각 29 → 각 29(변함 없음). 동시에 진행한 업로드는 최대 3개였습니다. 평균 응답 지연은 80ms·300ms 설정과 일치(318~341ms)해, 시간 감소는 서버가 빨라진 것이 아니라 **요청 수와 직렬 구간이 줄어든 결과**입니다.

로컬 단계(JSON 선택 → 미리보기 → 항목 확인 → 복구 백업 만들기)는 개선 전후 모두 **0.2~0.7초**로 병목이 아니었습니다.

남은 시간의 대부분은 파일마다 필요한 업로드 시작·본문 2요청(58개)과 복구 백업 저장입니다.

## 진행 표시

`3/27개 저장 완료 · 아이디어 저장`처럼 **저장된 수/전체와 현재 단계**를 보여 줍니다. 단계는 복구 백업 저장, 폴더 저장, 이미지 저장, 아이디어 저장, 기존 아이디어 갱신, 서버 재조회 검증입니다. 실패하면 `n/27개 저장 완료 · 실패 지점부터 재시도할 수 있습니다.`라고 알립니다. 전체 개수는 시작 시점부터 알고 있습니다.

## 중복 검토와 상태·링크 갱신

JSON 가져오기에서 **수정한 결과 확인** 뒤, 기존 아이디어와 겹치는 항목을 `중복 검토`에 보여 줍니다.

| 일치 기준 | 설명                                                                               |
| --------- | ---------------------------------------------------------------------------------- |
| 같은 ID   | 이전에 가져온(또는 같은 ID의) 아이디어                                             |
| 같은 출처 | 같은 `provenance`(Word·JSON 가져오기 출처)                                         |
| 제목+본문 | 공백·대소문자·전각/반각을 무시하고 같음. 본문이 없는 항목은 제목만으로 합치지 않음 |
| 같은 파일 | 같은 파일의 앞선 항목과 같음                                                       |

겹치는 항목은 **기본적으로 건너뜁니다.** 항목마다 `건너뛰기`, `새 아이디어로 추가`(같은 ID는 불가), `완료 상태·GitHub 링크만 갱신`을 고를 수 있습니다. 갱신을 승인하면 **완료 상태와 새 GitHub 링크만** 바뀌고, 제목·본문·이미지·태그·웹사이트 링크는 그대로입니다(불변 리비전으로 새 버전을 쌓으며 이전 버전은 남습니다). 복구 백업에는 선택과 관계없이 파일의 모든 항목이 보존됩니다. 미리보기 이후 기존 아이디어가 바뀌었다면(다른 기기에서 수정 등) 갱신하지 않고 다시 검토하라고 알립니다.

## 부분 성공 후 다시 실행

- 이미 저장된 아이디어는 같은 내용의 리비전이 있으면 건너뜁니다(이후 수정됐어도 중복 생성하지 않음).
- 이미 적용된 갱신은 건너뜁니다.
- 중간에 멈춘 실행을 재개하면 미리보기에서 한 선택이 그대로 적용됩니다(기기에 선택을 저장).
- 같은 JSON을 다시 가져오면 모두 "같은 ID"로 인식해 건너뜁니다.

## 남은 한계

- 실제 Google Drive에서의 속도와 속도 제한(동시성 3이 적절한지)은 측정하지 못했습니다. 동시성은 `WRITE_CONCURRENCY`로 조정할 수 있고, 429를 받으면 스스로 낮춥니다.
- multipart 업로드는 적용하지 않았습니다.
- Word 가져오기의 병합(`merge`)은 기존 동작 그대로이며, 완료·GitHub 갱신은 JSON 가져오기에만 있습니다.
- 가져오기 도중 앱을 닫으면 진행 중이던 파일은 Drive에 남을 수 있습니다. 이름이 내용 해시라서 다시 실행하면 같은 파일을 재사용합니다.
